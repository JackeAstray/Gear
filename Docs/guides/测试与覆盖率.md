# 测试与覆盖率门槛

> 面向维护者。讲清楚「测什么、跑什么命令、CI 拦住什么」，以及为什么覆盖率包没有常驻 manifest。

## 1. 本地怎么跑

```powershell
# 语法检查（不依赖 Unity，秒级；改完先跑这个）
dotnet run --project Tools/SyntaxCheck -- Unity/Gear/Assets/Gear

# EditMode + PlayMode 测试 + 架构守卫（需要 Unity 编辑器路径）
powershell -ExecutionPolicy Bypass -File Tools/unity-verify.ps1 `
    -UnityPath "E:/UnityEditor/6000.3.10f1/Editor/Unity.exe"

# 只跑测试、顺带生成覆盖率（需要工程装有 com.unity.testtools.codecoverage）
Unity.exe -batchmode -nographics -quit `
    -projectPath Unity/Gear `
    -runTests -testPlatform editmode `
    -testResults Unity/Gear/TestResults/editmode-results.xml `
    -enableCodeCoverage -coverageOptions "generateAdditionalMetrics;assemblyFilters:+Gear.*" `
    -logFile -
```

日志固定落在 `Unity/Gear/Logs/verify/`（`editmode.log` / `playmode.log` / `guard.log`），失败时先看这里。

## 2. CI 拦住什么

`.github/workflows/unity-ci.yml` 的 EditMode 作业里，测试跑完后有一道 **用例数与覆盖率门槛**（`Tools/CoverageGate`）：

| 检查 | 何时生效 | 不过会怎样 |
|---|---|---|
| 用例失败数 = 0 | 始终 | 失败 |
| 用例总数 ≥ `Tools/CoverageGate/baseline.json` 的 `minTests` | 始终 | 失败 |
| 行覆盖率 ≥ `minCoverage` | 有覆盖率数据时 | 失败 |
| 必须存在覆盖率数据 | 传了 `--require-coverage` | 失败 |

用例数棘轮的意义：删测试、或者测试文件因为 asmdef / 宏被静默排除出编译，都会让总数下降。只允许上调基线，改基线要单独一个提交说明原因。

```powershell
# 本地跑同一道门槛（结果是 Unity Test Runner 的 NUnit XML）
dotnet run --project Tools/CoverageGate -- --results Unity/Gear/TestResults
```

门槛参数：`--min-tests` / `--min-coverage` / `--require-coverage` / `--baseline <json>` / `--results <目录>`。
没有覆盖率数据时默认只告警、不失败，这样没装包的机器也能跑。

## 3. 关于 `com.unity.testtools.codecoverage`

**这个包没有写进 `Packages/manifest.json`**，原因很实际：

- 本机（以及任何离线环境）打开工程时，Unity 会尝试解析 manifest 里的每个包；本地没有缓存又没网络时，
  解析会卡在导入阶段，工程直接打不开 —— 为了一个只在 CI 用的包付出「离线不能开工程」的代价不划算。
- 因此 CI 在**工作区临时注入**：设置仓库变量 `GEAR_ENABLE_COVERAGE=true` 后，CI 会往 manifest 写一行
  再跑测试，并给测试加 `-enableCodeCoverage`；没有该变量时一切照旧。

启用步骤：

1. 仓库 → Settings → Secrets and variables → Actions → Variables → 新建 `GEAR_ENABLE_COVERAGE` = `true`。
2. 观察一轮 CI，确认注入的版本（当前写的 `1.2.6`）能被 Unity 解析；不匹配就改 `.github/workflows/unity-ci.yml`
   里注入的那一行版本号。
3. 拿到第一份覆盖率后，把 `Tools/CoverageGate/baseline.json` 的 `minCoverage` 设成略低于实测值
   （例如实测 41.2% → 设 40），之后只允许上调。

## 4. 回归测试该写在哪

| 改动 | 用例位置 | 参考 |
|---|---|---|
| 网络编解码 / 握手 / 防重放 | `Tests/NetworkHandshakeTests.cs`、`Tests/NetworkCodecTests.cs` | `EncryptedCodec_ReplayedFrame_IsRejected` |
| 下载/HTTP | `Tests/HttpMgrTests.cs`、`Tests/DownloadIntegrityTests.cs` | — |
| UI 窗口目录 / 模态栈 | `Tests/UIWindowCatalogTests.cs`、`Tests/UIModalStackTests.cs` | `AssemblyLoad_InvalidatesCatalog_AndRescanFindsTypes` |
| 计时器 / 对象池 | `Tests/TimerTests.cs`、`Tests/ObjectPoolPrewarmTests.cs` | — |

写回归测试的原则：**先能复现失败**（注释里写清「修复前这里会返回 true / 会抛异常」），
再断言修复后的行为；只为「看起来像测试」而写的断言没有价值。

## 5. 与架构守卫的关系

`Tools/SyntaxCheck` + `ArchitectureGuard` + 本门槛是三件不同的事，别混：

- **SyntaxCheck**：能不能解析（不需要 Unity，最快）。
- **ArchitectureGuard**：分层依赖、`.Instance` 只减不增、单文件行数、`[ModuleOrder]`、旧命名残留。
- **CoverageGate**：测了多少、过了多少、覆盖多少。

前两者在「架构守卫（不跑 Unity）」作业里跑，改动秒级反馈；后者依赖真实跑一遍测试。
